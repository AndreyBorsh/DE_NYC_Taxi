# DE_NYC_Taxi — ETL/ELT-пайплайн на данных нью-йоркского такси

Учебный проект по дата-инженерии: сырые месячные parquet-файлы NYC TLC проходят
путь от загрузки до аналитической витрины в PostgreSQL, построенной по схеме
«звезда».

**Стек:** Python (pandas, psycopg2, requests) · PostgreSQL · SQL · Docker · Git

---

## Архитектура

```
NYC TLC (parquet + csv)
      │  src/download.py — скачивание, идемпотентно, атомарная запись
      ▼
   data/raw/                          локальные файлы
      │  src/load_raw.py — загрузка через COPY
      ▼
raw.yellow_trips · raw.taxi_zone_lookup        слой сырья «как есть»
      │  sql/03_transform.sql — фильтры качества, приведение типов
      ▼
core.fact_trips                                схема «звезда»
  ├── core.dim_zone (посадка и высадка)
  ├── core.dim_date
  └── core.dim_payment_type
      │  sql/04_analytics.sql
      ▼
   аналитические запросы
```

Данные разделены на два слоя. **raw** хранит сырьё в том виде, в каком его отдал
источник, — без ограничений и без очистки. **core** содержит очищенные данные в
модели «звезда» и гарантирует качество через PK, FK и NOT NULL. Граница между
слоями — единственное место, где происходит отбраковка и приведение типов.

## Как запустить

Требуется Python 3.11+ и запущенный PostgreSQL (например, в Docker).

```bash
pip install -r requirements.txt
```

1. Применить DDL: выполнить `sql/01_raw_schema.sql` и `sql/02_core_schema.sql`
   в своей базе (через psql или любой SQL-клиент).

2. Скачать данные за нужный месяц:

```bash
python src/download.py 2024-01
```

3. Загрузить сырьё в базу:

```bash
python src/load_raw.py 2024-01
```

4. Выполнить `sql/03_transform.sql` — наполнит измерения и таблицу фактов.

5. Выполнить `sql/04_analytics.sql` — примеры аналитики поверх витрины.

Параметры подключения к базе задаются константой `DSN` в `src/load_raw.py`.

## Модель данных

Витрина построена по схеме «звезда»: в центре таблица фактов с метриками и
ключами, вокруг — измерения с описательными атрибутами. Такая денормализация
осознанна: данные читаются часто и агрегатами, поэтому меньшее число джойнов
важнее экономии места.

**Грань факта:** одна строка `core.fact_trips` = одна поездка.

| Таблица | Назначение |
|---|---|
| `fact_trips` | метрики поездки: сумма, чаевые, дистанция, длительность, пассажиры |
| `dim_zone` | район, зона, тип зоны (265 строк) |
| `dim_date` | год, квартал, месяц, день недели, признак выходного |
| `dim_payment_type` | расшифровка кодов способа оплаты |

Три проектных решения, которые стоит отметить:

**Role-playing dimension.** Зона участвует в поездке дважды — как место посадки и
как место высадки. Вместо двух одинаковых справочников заведено одно измерение,
на которое факт ссылается двумя ключами (`pickup_zone_key`, `dropoff_zone_key`).

**Генерация календаря.** У `dim_date` нет источника: даты порождаются через
`generate_series` за загружаемый период. Выборка дат из самих поездок дала бы
разрывы в дни без поездок и потребовала бы сканирования миллионов строк ради
трёх десятков значений.

**SCD Type 1 для зон.** При повторной загрузке атрибуты зоны перезаписываются
(`ON CONFLICT DO UPDATE`), история изменений не хранится. Для справочника
городских зон этого достаточно; версионирование потребовало бы Type 2.

Производные метрики (`duration_min`, ключ даты) вычисляются один раз при
трансформации и хранятся в факте — вместо пересчёта в каждом запросе.

## Инженерные решения

**COPY вместо `to_sql` / построчных INSERT.** Массовая вставка идёт одним потоком
через `copy_expert` из CSV-буфера в памяти, без пооперационного оверхеда на
каждую из трёх миллионов строк.

**Идемпотентность на трёх уровнях.** Повторный запуск пайплайна не должен
задваивать данные — это базовое требование, потому что упавшие задачи
перезапускают:

- `download.py` пропускает уже скачанный файл;
- `load_raw.py` перед вставкой удаляет строки этого же файла
  (`DELETE ... WHERE _src_file = ...`), справочник перезаливается целиком;
- `03_transform.sql` перед вставкой удаляет из факта строки загружаемого периода.

Для поездок используется выборочное удаление, для маленького справочника —
полная перезаливка: разные операции под разные задачи.

**Атомарная запись при скачивании.** Файл пишется во временный `.part` и
переименовывается только после успешного завершения. Обрыв соединения не
оставляет недокачанный файл, который следующий запуск принял бы за готовый.

**ELT, а не ETL.** Трансформация выполняется средствами SQL внутри базы, а не в
pandas: не упирается в память, ближе к промышленной практике DWH.

**Raw без ограничений, core со строгими.** В сыром слое нет NOT NULL, ключей и
проверок — загрузка не должна падать из-за качества данных, а сырьё остаётся
доказательством того, что реально прислал источник, и позволяет переиграть
трансформацию заново. Ограничения появляются в core, который обещает
потребителям чистые данные.

**Денежные суммы в `numeric(10,2)`, а не `double precision`.** Плавающая точка не
хранит десятичные дроби точно, и при агрегации миллионов строк накапливается
погрешность.

**Технические поля `_src_file` и `_loaded_at`** в сыром слое фиксируют
происхождение строки и служат основой идемпотентности.

**Параметризованные запросы** вместо подстановки значений в SQL строкой.

## Качество данных

Правила отбраковки на границе raw → core:

| Правило | Причина |
|---|---|
| дата посадки вне загружаемого месяца | в файле встречаются поездки других лет |
| высадка не позже посадки | некорректная запись времени |
| `total_amount <= 0` | возвраты и ошибки тарификации |
| `trip_distance <= 0` | поездка не состоялась |
| зона или способ оплаты отсутствуют в справочнике | нарушили бы целостность |

Результат загрузки за январь 2024:

```
raw.yellow_trips     2 964 624 строки
core.fact_trips      2 871 892 строки
отбраковано             92 732 строки (3,1 %)
```

Период определяется одной колонкой — временем посадки. Одинаковый критерий в
`DELETE` и `INSERT` гарантирует, что поездки на стыке месяцев не теряются и не
дублируются.

## Примеры аналитики

`sql/04_analytics.sql` содержит запросы, покрывающие все измерения:

- выручка, число поездок и средний чек по районам посадки;
- суточный профиль спроса: поездки, средние чаевые и длительность по часам;
- будни против выходных в разрезе способов оплаты, с долей внутри группы
  (оконная функция поверх агрегата);
- топ-3 зоны посадки внутри каждого района (`row_number` с фильтром по рангу).

## Известные ограничения

- parquet читается в память целиком (~400 МБ на месяц) — подход не масштабируется
  на годовые объёмы, потребуется чтение частями или Spark;
- загружаемый месяц указывается в SQL вручную, параметризации нет;
- измерение зон реализовано как SCD Type 1 — история изменений не сохраняется;
- временные `.part`-файлы после обрыва скачивания не подчищаются автоматически;
- нет автоматических проверок качества данных и тестов.
